# 相似专题 UI/UX 实施计划

## 1. 总体依赖关系

```text
                 ┌──────────────────────┐
                 │ PRD-02 能力进度与解锁 │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │ PRD-01 学习图谱入口   │
                 └──────────────────────┘

┌──────────────────────┐
│ PRD-03 题图直接操作   │
└──────────┬───────────┘
           │
           ├──────────────┐
           ▼              ▼
┌──────────────────────────────────────┐
│ PRD-04 多前置综合挑战关               │
│ 同时依赖 PRD-02 的能力真值和           │
│ PRD-03 的结构化动作证据                │
└──────────────────┬───────────────────┘
                   ▼
┌──────────────────────────────────────┐
│ PRD-05 失败诊断与补强回路             │
└──────────────────────────────────────┘
```

关键路径：

```text
契约冻结 → PRD-02 + PRD-03 → PRD-04 → PRD-05
```

PRD-01 不在挑战闭环的关键路径上，但必须等 PRD-02 提供真实节点状态后才能完成集成。

## 2. 阶段 0：共同契约冻结（串行）

开始任何页面开发前，先完成一轮小范围契约设计。这个阶段必须串行完成，否则三条开发线会各自发明一套能力 ID 和状态语义。

### 必须冻结的内容

1. 七个首版 `capabilityId`。
2. 五个专题节点和依赖边。
3. runtime step 到 capability 的证据映射。
4. 节点状态：`locked / available / in_progress / mastered`。
5. session 类型：`practice / challenge / remediation`。
6. challenge、remediation 和原始 session 的关联字段。
7. 图谱状态接口的最小响应结构。

### 允许后续调整的内容

- 地图节点坐标和视觉布局。
- 掌握规则中的题数阈值。
- 挑战题数量。
- 补强题数量。
- 动效和装饰视觉。

### 阶段出口

- 前后端共享类型能够编译。
- 每个现有专题步骤都能映射到 capability 或明确标记为“不产生掌握证据”。
- 产品、内容和工程使用同一份节点与能力 ID 表。

## 3. 阶段 1：三条泳道并行开发

### 泳道 A：PRD-02 能力进度与解锁

负责服务端事实源：

- 能力证据数据结构与存储。
- 节点进度与掌握状态计算。
- 解锁与推荐节点计算。
- 学习图谱状态 API。
- 规则版本化和单元测试。

前期可以使用现有 action event 和测试 fixture，不等待新 UI。

### 泳道 B：PRD-03 题图直接操作

按操作原语逐个替换现有外部槽位：

1. 点边标数。
2. 配对应边。
3. 作平行辅助线。
4. 共线边互化。
5. 列式结构槽。
6. 局部撤销与对象级错误反馈。

先保持现有判题协议，确保 UX 改造可以独立上线。能力证据字段按阶段 0 的契约同步写入 action event。

### 泳道 C：PRD-01 图谱 UI 骨架 + 内容准备

图谱前端可使用固定 fixture 开发：

- 地图布局与响应式重排。
- 节点选择和详情面板。
- 五种节点状态展示。
- 锁定原因与前置跳转。
- 路由进入 Learn / Practice / Review。

同时进行不阻塞工程的内容准备：

- 确认五专题的唯一能力标签。
- 筛选候选挑战题。
- 为后续补强准备 capability 对应题目池。

### 并行边界

- 泳道 C 不在前端实现临时解锁算法。
- 泳道 B 不负责决定 capability 是否 mastered。
- 泳道 A 不依赖具体地图坐标和视觉组件。

## 4. 阶段 2：第一次汇合——普通学习闭环

这一阶段将 PRD-01、PRD-02、PRD-03 接成一个端到端闭环。

### 集成路径

```text
学生从地图选择专题
  → 进入 Learn / Practice
  → 在题图上完成结构化动作
  → 服务端记录 capability evidence
  → 重算进度与解锁
  → 返回地图看到新状态
```

### 必须验证

1. Learn 只能产生学习进度，不能单独产生 mastered。
2. Practice 中的直接操作能够产生动作级证据。
3. 刷新地图后节点状态保持一致。
4. 锁定节点能够定位具体缺失前置。
5. 当前未完成 session 仍能恢复。

### 阶段出口

先发布不含挑战关的版本：

- 五专题图谱可用。
- 普通学习、训练、复盘可用。
- 直接操作替代外部槽位。
- 解锁状态由服务端返回。

这是第一个完整、可独立创造价值的发布节点。

## 5. 阶段 3：PRD-04 综合挑战关

只有阶段 2 稳定后才开始端到端挑战开发。此阶段内部仍可三线并行。

### 后端线

- `challenge` session 类型。
- 多 capability 证据规则。
- 提前挑战、通过和失败状态。
- 挑战通过后的能力证据写入与重新解锁。

### Runtime 线

- 复用 PRD-03 的直接操作组件。
- 保证核心动作无法通过只填最终答案绕过。
- 记录挑战失败的 `focusStepId` 与 `diagnosisCode`。

### 地图与内容线

- 加入独立形状的挑战节点。
- 显示“已具备 / 尚缺失”的推荐前置。
- 提供“先补前置 / 直接挑战”。
- 固定首版挑战场景和证据要求。

### 阶段出口

- 未满足推荐前置仍可挑战。
- 挑战成功可以验证并解锁能力。
- 挑战失败能返回结构化诊断，但此时可以暂时只支持“重试”或“去专题学习”。

## 6. 阶段 4：PRD-05 补强回路

PRD-05 必须串在 PRD-04 之后，因为没有真实 challenge session 和失败诊断，就无法验证断点返回。

### 可提前并行的准备工作

这些工作可以在阶段 3 开始时提前进行：

- `diagnosisCode → capabilityId` 映射审计。
- 每个 capability 的补强题池检查。
- 诊断文案与 fallback move 评审。
- 判断哪些步骤可安全恢复，哪些必须重启当前题。

### 正式开发内容

- `remediation` session 类型。
- challenge → remediation → challenge 的 session lineage。
- 精准失败反馈页。
- 短补强任务组装。
- 原挑战断点恢复或当前题重启。
- Review 中展示挑战、补强和重试的关联。

### 阶段出口

```text
挑战失败
  → 定位一个核心能力缺口
  → 完成短补强
  → 返回原挑战
  → 再次作答并通过
```

整条链路在刷新、退出和重新进入后仍可恢复。

## 7. 阶段 5：统一验收与逐步放量

### 回归范围

- 普通任务树中的其他章节不受图谱影响。
- Learn / Practice / Review 路由职责不变。
- 旧 session 仍可恢复或有明确迁移策略。
- 旧 ResultSnapshot 仍可打开复盘。
- 五专题所有操作支持鼠标、触摸与键盘。

### 发布顺序

建议拆成四次发布：

| 发布 | 内容 | 是否依赖后续功能 |
| --- | --- | --- |
| Release A | PRD-03 题图直接操作 | 否，可独立回滚 |
| Release B | PRD-02 + PRD-01 普通学习图谱 | 否，不含挑战 |
| Release C | PRD-04 综合挑战关 | 依赖 A、B |
| Release D | PRD-05 精准补强回路 | 依赖 C |

如果 PRD-02 比 PRD-03 更早完成，Release A 与 B 可以交换，但不应为等待整套图谱而延迟已完成的直接操作改进。

## 8. 三泳道责任表

| 阶段 | 数据与后端 | Runtime 交互 | 地图与产品页面 |
| --- | --- | --- | --- |
| 0 | 共同契约 | 共同契约 | 共同契约 |
| 1 | PRD-02 | PRD-03 | PRD-01 fixture + 内容准备 |
| 2 | 进度 API 集成 | evidence 接入 | 图谱真实状态接入 |
| 3 | challenge session | 挑战动作与证据 | 挑战节点与入口 |
| 4 | remediation lineage | 补强 runtime | 失败反馈与返回体验 |
| 5 | 迁移、监控 | 全量回归 | 响应式与可用性验收 |

## 9. 关键风险与控制点

### 风险 1：图谱 UI 先行，解锁逻辑被写进前端

控制：PRD-01 在阶段 1 只使用 fixture；真实上线必须接 PRD-02 API。

### 风险 2：能力粒度过细，进度永远无法稳定

控制：首版只保留能映射到可观察学生动作的七个 capability。

### 风险 3：挑战只验证最终答案

控制：PRD-04 必须等待 PRD-03 的结构化动作证据稳定。

### 风险 4：补强功能先做页面，后补 session 关系

控制：PRD-05 先实现 lineage 和 resume contract，再做失败反馈页面。

### 风险 5：内容标注成为最后的阻塞项

控制：挑战题筛选、capability 标注和补强题池审计从阶段 1 并行开始。

## 10. 总体验收门槛

以下条件全部满足后，整套改版才算完成：

1. 地图状态有唯一服务端真值。
2. 直接操作不依赖非必要外部槽位。
3. 挑战可以提前尝试并依据过程证据通过。
4. 挑战失败能定位到具体 capability。
5. 补强完成后能够返回原挑战上下文。
6. 旧学习、训练、复盘记录没有被破坏。
