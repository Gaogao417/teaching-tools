# ADR-001 Runtime-First Architecture

## 背景

早期实现按页面和题型直接堆叠：

- `PracticePage` 同时承担 session、题型渲染、输入控件、提示、反馈
- 后端只提供题型字段，前端自行推导大量交互含义
- 文档按页面拆散，没有项目级边界

这种结构在只有少量题型时尚能运行，但会在题型增长时快速失控。

## 决策

项目采用 runtime-first 架构：

- 练习页只有一个运行时页面
- 题型被视为教学关卡内容实例
- 后端负责规则、真值和步骤推进
- 前端负责运行时宿主、工作区渲染和引导反馈
- 共享契约围绕 `ExerciseRuntimeSpec` 和标准动作事件设计

## 影响

- `PracticePage` 需要重构为 runtime host
- 组件库要按工作区对象和引导反馈对象拆分
- 后端需要输出 runtime-first 数据，而不是只输出题型字段
- 新题型接入成本会下降，但前期抽象成本会上升

## 备选方案

### 方案 A: 按题型继续扩页面分支

优点：

- 短期改动快

缺点：

- 页面会持续膨胀
- 边界越来越模糊
- 无法支持长期题型增长

### 方案 B: 后端直接远程控制前端模板

优点：

- 看似灵活

缺点：

- 前端实现细节泄漏到后端
- DSL 失控
- 组件库无法稳定复用

最终不采用。
